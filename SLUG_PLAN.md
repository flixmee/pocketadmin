# Slug Field Plan

## Goal
Add a dedicated `slug` field type with an attached field option so records can keep a URL-friendly slug in sync with another field when desired.

## Current baseline
- `TextField` already supports autogenerated values with `AutogeneratePattern` and the `:autogenerate` setter modifier.
- There is no dedicated `slug` field type in `core/` yet.
- Field types are registered through `Fields[FieldTypeX]` in their own `init()` functions.
- Existing field types follow a consistent pattern: struct definition, field registration, validation, record interception, and tests.

## Assumption
- "Attached field option" means the slug field can reference another field as its source and derive the slug from that source value.
- If that assumption is wrong, the plan should be adjusted before implementation.

## Proposed design
1. Add a new `SlugField` type in `core/`.
2. Model it as a text-like field, but with slug-specific behavior and validation.
3. Add an attached/source field option, likely something like `AttachedField` or `SourceField`, that stores the field name or id used to generate the slug.
4. Normalize values to a slug-safe format during prepare/intercept steps.
5. Allow manual overrides only if that is consistent with the intended product behavior; otherwise keep the slug derived from the attached field.

## Implementation tasks
- Add the new field type constant and register it in `Fields`.
- Define the `SlugField` struct with the minimum set of shared field properties and slug-specific options.
- Implement `Type`, `GetId`, `SetId`, `GetName`, `SetName`, `GetSystem`, `SetSystem`, `GetHidden`, `SetHidden`, `ColumnType`, `PrepareValue`, `ValidateValue`, and `ValidateSettings`.
- Decide whether the slug field should embed or reuse text-field helpers for string validation and autogeneration.
- Implement record interception so the slug updates when the attached field changes and the slug is empty or configured to stay synced.
- Extend setter support if the field needs a custom modifier for attached-field updates or manual regeneration.
- Add serialization tags for the new option so it persists through API and migrations.
- Update any field factory, cloning, import/export, or schema code that assumes a fixed list of field types.

## Validation rules to define
- Slug values should be lowercased and restricted to safe slug characters.
- Empty slugs should only be allowed when the field is not required.
- The attached field should exist and be compatible with slug generation.
- Prevent invalid references, self-references, and circular dependencies if the slug field can attach to other derived fields.
- Define collision handling for duplicate slugs, especially if the slug must be unique within a collection.

## Tests to add
- Field construction and base-method coverage for the new field type.
- Validation tests for the attached field option and slug formatting rules.
- Value preparation tests for slug normalization.
- Interception tests for auto-sync behavior from the attached field.
- Setter tests if a custom modifier is added.
- Collection serialization/import/export tests for the new field option.
- Migration or compatibility tests if the field type must be supported in generated snapshots or old data.

## Open questions
- Should the slug be automatically generated from the attached field, or only on demand?
- Should manual edits be preserved after the source field changes?
- Should uniqueness be enforced at the field level, the collection level, or only by convention?
- Should this be implemented as a new field type or as an option on `TextField` instead?

## Acceptance criteria
- A slug field can be created, validated, serialized, and round-tripped through collection definitions.
- An attached field option can drive slug generation from another field.
- Tests cover the core behavior and edge cases.
- The plan is ready to break into implementation steps without additional design work.
